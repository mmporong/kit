# kit

작업 범위 정리·데이터 감사·검증·디버깅·구현 설명을 돕는 **선택형 Skill 5개**입니다.
완성 답안이나 앱이 아니라, 제공된 코딩 에이전트가 참고할 작업 절차입니다.
MCP·개인 API 키·새 모델·전역 설치는 필요하지 않습니다.

**빠른 시작은 아래 1절, 스킬별 상세 설명은 4절의 펼치기 항목을 보세요.**

> 현재 과제 안내와 운영 규정이 항상 우선합니다. 이 저장소는 공식 승인 자료가 아니며,
> 실제 코파 환경의 자동 인식·설치 성공과 성능 향상은 검증하지 않았습니다.
> AI 사용이 금지된 단계 또는 제출물 확정 이후에는 사용을 중단합니다.

## 1. 바로 사용하기

### 1-1. 실제 과제 폴더의 일반 터미널에서 가져오기

**준비 저장소가 아니라 실제 과제의 README와 소스가 있는 폴더에서 실행합니다.**
아래는 셸 명령이며 Codex 대화 입력창에 넣는 요청문이 아닙니다.

```bash
kit_dir=$(mktemp -d) && \
git clone --depth 1 https://github.com/mmporong/kit.git "$kit_dir"
```

복제한 `install.sh`와 `KIT.md`를 확인한 뒤, **같은 터미널에서** 설치합니다.

```bash
bash "$kit_dir/install.sh" "$PWD"
```

첫 명령의 `git clone`은 공개 자료를 다운로드합니다. 반면 `install.sh` 자체에는
네트워크 호출·Git 작업·패키지 설치·Codex 실행 또는 업데이트가 없습니다.
접근이 차단되면 다른 경로로 우회하지 마세요.

### 1-2. 같은 과제 폴더에서 제공된 Codex 사용

새 대화를 시작하는 경우:

```bash
codex
```

이미 Codex와 작업 중이면 설치 때문에 대화를 무조건 종료하지 마세요.
**현재 대화에서 다음 파일을 명시적으로 읽히는 방법**부터 사용할 수 있습니다.

첫 요청은 한 줄이면 됩니다. 자료 확인과 세부 절차는 스킬 안에 들어 있습니다.

```text
$kit-brief 현재 과제를 분석해 주세요.
```

### 1-3. 필요한 스킬만 선택

다음은 **Codex의 대화 입력창**에 넣는 요청입니다. `$kit-...`를 일반 셸에 입력하지 마세요.

| 상황 | 요청 예시 | 확인할 결과 |
|---|---|---|
| 처음 시작·요구 변경 | `$kit-brief 현재 과제를 분석해 주세요.` | 필수·선택 요구, 완료·검증 조건, 담당자 질문, 첫 구현 흐름 |
| 표·CSV·로그 분석 | `$kit-data 현재 과제의 데이터를 점검해 주세요.` | 관측 단위·키·재검사·분모, 실제 계산과 미확정 정의 |
| 기능 완료·제출 확정 전 | `$kit-verify 현재 과제를 검증해 주세요.` | 요구별 통과·실패·미확인과 실행 근거 |
| 원인이 불명확한 오류 | `$kit-debug 현재 오류를 해결해 주세요.` | 재현·원인 근거·최소 수정·회귀 검사 |
| 제출 확정 전 복습 | `$kit-explain 현재 구현을 설명해 주세요.` | 실제 코드 흐름·선택 이유·검증 범위·한계 |

**선택 문법이나 자동 인식이 지원되지 않으면** 다음처럼 파일을 읽혀도 됩니다.

```text
.agents/skills/kit-data/SKILL.md를 읽고 현재 과제의 데이터를 점검해 주세요.
```

이 방법은 문서를 명시적으로 읽는 것이며, 자동 Skill 등록 성공과는 다릅니다.
자동 인식 여부를 확인하려고 Codex를 업데이트하거나 관리 설정을 바꾸지 마세요.

스킬이 현재 폴더의 과제 지침·KIT.md·README·관련 파일·기존 실행 방법을 찾아 읽습니다.
사용자는 파일 목록이나 절차를 매번 다시 적을 필요가 없습니다. 남은 시간이나 새 담당자 답변이 있으면 덧붙이세요.
없는 자료는 부재를 표시하고, 답에 따라 결과가 달라질 업무 규칙만 질문으로 정리합니다.
스킬은 질문을 전송하거나 담당자 답변을 만들어내지 않습니다. 분석·설명 호출은 구현·설치 승인이 아닙니다.

### 1-4. 테스트 판정과 예측 모델 평가

`kit-verify`는 테스트 0개·전부 skip을 미확인으로 남기며, 종료코드와 로그가 충돌하면 성공으로 판정하지 않습니다. 일부 skip은 실행한 범위와 분리하고 실패·오류를 숨기지 않습니다. 이전 증거는 검사 시점의 파일·설정·입력·의존성이 현재도 유효한 범위에서만 재사용합니다.

```text
$kit-verify 현재 과제를 검증해 주세요.
```

예측 모델을 학습·평가할 때만 `kit-data`의 [모델 평가 점검](skills/kit-data/references/model-evaluation.md)을 읽습니다. 기준선과 같은 평가셋에서 비교하고, 그룹·시간 누수, 학습·검증·최종 평가셋 분리, 혼동행렬과 오탐·미탐을 확인합니다. 단순 집계나 화면 수정에는 적용하지 않습니다.

```text
$kit-data 현재 예측 모델을 평가해 주세요.
```

자동 인식이 안 되면 `.agents/skills/kit-data/references/model-evaluation.md`를 명시해 읽힙니다. 검증 기록은 [선택형 양식](skills/kit-verify/references/evidence-log.md)을 참고합니다. 이 문서들은 자동 판정기나 성능 향상 보장이 아닙니다.

### 저장·집계가 실제로 작동하는지 확인하기

`kit-verify`에는 [실제 동작 확인](skills/kit-verify/references/runtime-behavior.md) 지침이 있습니다. 저장 후 별도 조회, 입력 변화에 따른 결과, 오류 응답과 남은 상태, 내보낸 파일의 내용을 확인합니다. 새 도구를 설치하지 않으며 자동 검사기가 아닙니다. 화면 연결은 사용자의 내장 미리보기 확인 전까지 미확인으로 둡니다.

### 1-5. kit-explain: 제출 전 서술형 준비

```text
$kit-explain 현재 프로젝트의 제출 전 서술형 복습을 준비해 주세요.
```

이 한 줄로 **해커톤 당일 현재 작업 폴더의 프로젝트**를 읽고 다음 결과를 만듭니다.

1. 목표·입출력·구조·구현·검증·한계를 담은 짧은 전체 요약.
2. 실제 알고리즘·데이터 사용·선택 이유·보장과 반례·협업 판단을 묻는 심화 연습 문제 10개. 해당하지 않는 개념은 실제 구현의 질문으로 바꿉니다.
3. 문항별 설명 답안, 파일·함수·검사 근거, 조건을 바꾼 꼬리 질문과 설명 포인트, 보조 암기 단서. 답은 한 줄 요약에 그치지 않고 작동 원리와 한계를 설명합니다.

작업 마무리·최종 검증 요청에도 검증 보고 뒤 이 절차를 연결합니다. 중간 수정마다 반복하지 않습니다. [서술형 복습 절차](skills/kit-explain/references/written-review.md)는 Cofa의 공개 사후 Q&A 안내를 참고한 연습 설계이며, 실제 기출이나 공식 모범답안이 아닙니다. 준비용 kit나 아직 없는 과제의 답을 미리 꾸미지 않습니다. AI 사용이 허용된 제출 확정 전까지만 수행하며 답안·코드·로그를 공개 저장소로 보내지 않습니다.

## 2. 무엇이 설치되고 어떻게 작동하나요?

### 실제 설치 결과

[install.sh](install.sh)는 다음 파일만 실제 과제 폴더에 추가합니다.

```text
실제 과제 폴더/
├── KIT.md
└── .agents/skills/
    ├── kit-brief/SKILL.md
    ├── kit-data/
    │   ├── SKILL.md
    │   └── references/
    │       ├── semiconductor.md
    │       └── model-evaluation.md
    ├── kit-verify/
    │   ├── SKILL.md
    │   └── references/
    │       ├── evidence-log.md
    │       └── runtime-behavior.md
    ├── kit-debug/SKILL.md
    └── kit-explain/
        ├── SKILL.md
        └── references/written-review.md
```

기존 `AGENTS.md`, `AGENTS.override.md`, 소스, 의존성, 모델·권한 설정은 변경하지 않습니다.
이 저장소의 [AGENTS.md](AGENTS.md)는 **키트 자체를 수정하는 개발용 지침**이므로 과제 폴더로 복사하지 않습니다.
과제에서 읽힐 공통 지침은 [KIT.md](KIT.md)입니다. 각 스킬이 이를 읽도록 지시하며 자동 적용을 가정하지 않습니다.

같은 경로에 다른 내용이 있으면 복사 전에 중단하며, 동일한 내용의 재설치는 재사용합니다.
설치 중 다른 프로세스가 같은 경로를 변경하지 않는 단일 실행을 전제로 합니다.
시스템 장애나 동시 쓰기에 대한 완전한 트랜잭션·자동 복구를 제공하지 않습니다.

### 한 스킬의 내부 구성

각 `SKILL.md`에는 다음이 들어 있습니다. 아래 설명은 현재 저장소 파일을 기준으로 합니다.

| 구성 | 역할 |
|---|---|
| `name` | `kit-data`처럼 스킬을 구분하는 이름 |
| `description` | 언제 사용하고 언제 생략할지 알려주는 짧은 설명 |
| 입력 확보 | 목표만 받아도 과제 문서·파일·기준·로그를 찾아 확인 |
| 처리 | 에이전트가 확인하고 실행할 순서 |
| 출력 | 결과에 포함해야 할 근거·판정·한계 |
| 실패·생략 기준 | 자료 부재·도구 제한·미확정 업무 규칙·유효한 기존 증거의 처리 |
| 공통 경계 | 기존 지침 우선, 외부 전송·설정 변경 금지, 미실행 구분 |
| `references/` | 해당 상황에서만 읽을 추가 자료. 데이터·검증·설명 스킬에 포함 |

OpenAI의 일반 Skill 설명은 메타데이터로 스킬을 발견하고 필요할 때 본문과 참고자료를 읽는 방식을 안내합니다.
다만 제공된 고정 버전이 같은 방식으로 인식하는지는 실제 환경에서 확인해야 합니다.
참고: [OpenAI Skills](https://developers.openai.com/plugins/concepts/skills).

### 스킬 사용 전후에 달라지는 것

```text
기본 요청
  사용자 요청 + 과제 파일
  → 에이전트가 작업 방법을 정함

스킬을 읽힌 요청
  사용자 요청 + 같은 과제 파일 + 선택한 작업 절차
  → 필요한 확인과 실행
  → 근거·상태·한계를 포함한 결과
```

**원본 입력을 자동으로 바꾸거나 별도 모델을 학습시키는 구성은 아닙니다.**
현재 다섯 스킬에는 데이터 분석 실행 스크립트, 서버, MCP, 브라우저 자동화, 실행 모델을 바꾸는 자동 라우터가 없습니다.
분석 코드 작성·테스트 실행·파일 수정은 제공된 코딩 에이전트와 허용된 도구가 수행합니다.
출력 항목은 지침이지 강제 JSON 스키마가 아니므로, 요구한 근거가 실제로 포함됐는지 사용자가 확인해야 합니다.

## 3. 상황별 진행 순서

```text
과제 문서·기존 프로젝트
  → kit-brief: 목표와 완료 조건 정리
  → 데이터가 있으면 kit-data: 의미와 계산 기준 확인
  → 기본 Codex: 작은 사용자 흐름 하나 구현
  → kit-verify: 실제 요구와 실행 결과 대조
      ↳ 원인이 불명확한 실패: kit-debug → 영향받은 조건 재검증
  → 제출 확정 전 kit-explain: 내가 만든 결과 이해
  → 사용자가 저장·제출 확인, AI 사용 금지 단계에서는 중단
```

이 순서는 권장 연결 예시이지 자동 실행 파이프라인이 아닙니다.
별도의 구현 스킬이나 여러 에이전트를 반드시 실행하는 구조도 아닙니다.

- **처음 받는 과제:** `kit-brief`로 범위를 정하고 기본 Codex로 구현합니다.
- **집계·데이터 분석:** 계산 전에 `kit-data`, 구현·계산 후 `kit-verify`를 사용합니다.
- **기존 기능의 오류:** 이미 요구가 명확하면 `kit-brief`를 생략하고 `kit-debug`부터 사용합니다.
- **작고 명확한 변경:** 수정 지시 후 관련 검사만 합니다. 다섯 스킬을 모두 호출하지 않습니다.
- **담당자 답변으로 조건 변경:** `kit-brief`로 바뀐 가정과 영향 범위만 정리한 뒤 필요한 부분을 수정합니다.
- **제출 직전:** 검증 근거가 없는 필수 조건부터 확인하고, 설명 복습 때문에 제출 시간을 침범하지 않습니다.

다음 스킬로 넘길 때 이전 출력 전체를 매번 복사할 필요는 없습니다.
같은 작업 환경의 기존 문서·기록을 재사용하고, 중요한 변경·실제 답변·새로운 시간 제약만 전달하세요.
담당자에게 문의하는 행동과 답변의 진위는 사용자가 확인하며, 키트가 대화 내용을 만들어내면 안 됩니다.

<a id="skills-detail"></a>
## 4. 각 스킬의 구성·입력·처리·출력

아래 상세 설명은 연결된 `SKILL.md`의 절차를 풀어쓴 것입니다.
호출 예시와 기대 출력 예시는 **자체 합성 예시**이며 실제 시험 문제·실행 로그가 아닙니다.

<details>
<summary><strong>① kit-brief — 모호한 과제를 구현 가능한 조건으로 정리</strong></summary>

원문: [skills/kit-brief/SKILL.md](skills/kit-brief/SKILL.md)

### 언제 사용하나요?

과제를 처음 받았거나 담당자 답변으로 요구가 달라졌을 때 사용합니다.
이미 목표와 수정 위치가 확정된 작은 편집에는 생략합니다.

### 입력

실제 과제 안내, 제공 파일, 기존 실행 방법, 실제로 받은 담당자 답변, 남은 시간입니다.
없는 조건을 예시나 회사 이름에서 추정해 채우지 않습니다.

### 진행 방식

1. README·제공 자료·기존 코드 구조와 실행·테스트 방법을 찾고 목표를 한 문장으로 씁니다.
2. 필수·선택 요구를 나누고 각 요구에 근거·완료 조건·검증 방법·기대 결과를 연결합니다.
3. 확정 사항, 가정, 질문이 필요한 사항을 나눕니다.
4. 답에 따라 구현이나 판정이 달라질 질문만 사용자에게 제안합니다.
5. 핵심 정의가 불명확하면 해당 결정만 보류하고 기존 실행 확인 등 독립 작업을 진행합니다.
6. 남은 시간에 구현과 검증을 끝낼 수 있는 사용자 흐름 하나를 정합니다.
7. 새 답변이 도착하면 영향받는 가정·구현·검사만 갱신합니다.

### 출력

`확인 자료·실행 방법 / 목표 / 필수·선택 요구 / 근거 / 완료·검증 조건 / 담당자 질문 / 첫 구현 흐름`

새 문서가 반드시 생성되는 것은 아닙니다. 과제에서 정한 기록 양식이 있으면 사용하고,
별도 파일이 필요하지 않으면 대화에서 짧게 정리합니다.

### 호출 예시

```text
$kit-brief 현재 과제를 분석해 주세요.
```

### 기대 출력 예시

가상 요구가 “검사표를 읽어 검토 대상을 보여주고 최종 판정은 사람이 한다”라면:

- 목표: 담당자가 검토할 항목과 근거를 확인할 수 있게 합니다.
- 필수 조건: 원본 보존, 검토 대상 표시, 최종 판정 자동 확정 금지.
- 미확정 사항: 검토 우선순위를 어떤 기준으로 정할지 확인이 필요합니다.
- 첫 흐름: 파일 읽기 → 유효성 검사 → 기준이 확정된 항목의 결과 표시.
- 완료 기준: 알려진 작은 입력에서 지정된 항목과 근거가 일치합니다.

위 조건은 예시입니다. 실제 문서에 없는 기능을 기본 필수 요구처럼 넣지 않습니다.

### 사용자가 확인할 것

AI가 “있으면 좋겠다”라고 제안한 기능을 필수 요구로 바꾸지 않았는지 확인합니다.
담당자에게 질문할지, 어떤 제안을 채택할지는 실제 근거와 작업 범위에 맞춰 결정합니다.
**출력은 구현을 위한 조건 정리이지, 구현 완료가 아닙니다.**

<summary><strong>② kit-data — 계산 전에 데이터 의미·키·단위·분모를 감사</strong></summary>

원문: [skills/kit-data/SKILL.md](skills/kit-data/SKILL.md)

### 언제 사용하나요?

표·CSV·검사 이력·설비 로그를 집계하거나, 데이터를 이용해 예측하려 할 때 사용합니다.
데이터가 없는 UI 수정에는 필요하지 않습니다. 반도체 참고사항은 실제 해당 데이터일 때만 읽습니다.

### 입력

허용된 원본 파일, 데이터 사전, 계산할 지표나 분석 질문, 기준 문서입니다.
어떤 파일·열이 실제로 제공됐는지 먼저 확인하고 원본은 보존합니다.

### 진행 방식

1. 한 행이 나타내는 대상, 식별 키의 유일성 범위, 관측 시점·정보 가용 시점을 확인합니다.
2. 읽은 파일·행·열 수와 전체 검사인지 일부 표본인지 기록합니다.
3. `001` 같은 ID의 앞자리 0을 보존하고, 숫자처럼 보인다고 숫자형으로 단정하지 않습니다.
4. 공백·대소문자 등의 차이는 후보로만 제시합니다. `CH-01`과 `EQP-01`의 접두어를 제거해 같은 대상이라고 합치지 않습니다.
5. 결측·미측정·검사 실패·실제 0과 재검사 이력을 구분합니다.
6. 조인 전 키 중복과 관계를 확인하고, 조인 후 행 증가·미연결·수량 중복을 대조합니다.
7. 지표의 분자·분모·대상·기간·제외 조건·단위를 정합니다. 분모가 0이면 임의로 0%로 바꾸지 않습니다.
8. 예측 문제일 때만 미래 정보, 동일 개체·시간의 학습/시험 중복, 시험셋으로 전처리·임계값을 정했는지 확인합니다.
9. 계산은 실제 코드로 수행하고, 작은 합성 입력이나 별도의 산식과 대조합니다.

반도체 과제에서는 [semiconductor.md](skills/kit-data/references/semiconductor.md)를 추가로 읽습니다.
이 자료는 로트·웨이퍼·다이·검사 단계, 재검사, 규격/관리 한계 등의 **확인 항목**이며,
특정 공정의 규격값이나 실제 출제 내용을 제공하지 않습니다.

### 출력

`관측 단위·키·시간·단위 / 이상·미확정 정의 / 영향 범위 / 산식과 실행 결과 / 제외 이유 / 한계`

**자동 데이터 프로파일러가 포함된 것은 아닙니다.** 에이전트가 현재 환경의 도구로 분석 코드를 작성·실행해야 합니다.
도구나 파일 접근이 없으면 미확인으로 남깁니다. 지침을 읽었다는 이유로 감사 완료를 선언하지 않습니다.

### 호출 예시

```text
$kit-data 현재 과제의 데이터를 점검해 주세요.
```

### 입력과 출력이 달라지는 예시

자체 합성 입력:

| 제품 | 검사 차수 | 결과 |
|---|---:|---|
| A | 1 | 합격 |
| B | 1 | 불합격 |
| B | 2 | 합격 |
| C | 1 | 합격 |

각 제품의 이력이 표에 모두 있고 차수가 검사 순서를 뜻한다고 가정하면:

- 검사 기록 기준 합격 비율: `3 / 4 = 75%`
- 제품별 최초 검사 합격 비율: `2 / 3 ≈ 66.7%`
- 제품별 마지막 검사 합격 비율: `3 / 3 = 100%`

좋은 출력은 숫자 하나가 아니라 **“검사 기록 4건·제품 3개·B 재검사 있음·어떤 정의가 업무 지표인지 확인 필요”**까지 포함합니다.
이 예시는 산식을 설명하는 합성 사례이며, Skill 적용 전후의 모델 성능을 측정한 결과가 아닙니다.

### 사용자가 확인할 것

분모·재검사 정책·단위가 실제 문서와 맞는지 확인합니다.
규격값이나 라벨의 의미가 없으면 근거 없이 채우지 않고 미확정으로 남겨야 합니다.
관찰된 차이·상관관계·모델 지표를 곧바로 불량 원인이나 운영 안전성으로 해석하지 않습니다.

<summary><strong>③ kit-verify — 완료 주장을 실제 실행 근거와 대조</strong></summary>

원문: [skills/kit-verify/SKILL.md](skills/kit-verify/SKILL.md)

### 언제 사용하나요?

기능을 완성했다고 보고받았을 때, 수정 후 기존 동작을 확인할 때, 제출 전 누락을 찾을 때 사용합니다.
모든 검사를 매 요청마다 반복하기보다 현재 변경과 필수 조건에 맞는 검사를 고릅니다.

### 입력

확정된 완료 조건, 현재 코드·설정·데이터 버전, 최근 변경, 실제 실행 로그입니다.
코드만 있고 실행 로그가 없다면 실행 검증이 남아 있는 상태입니다.

### 진행 방식

1. 필수 파일과 기능이 실제로 있는지 확인하고 빈 양식·임시 문구를 구분합니다.
2. 허용된 환경에서 빌드·순수 로직·로컬 API 등 필요한 검사를 실행합니다.
3. 정상·경계·누락·중복 요청·실패 중 해당 요구를 깨뜨릴 수 있는 입력을 고릅니다.
4. 기대 결과는 과제 문서와 확정 규칙에서 정합니다. 구현을 베껴 테스트 정답으로 쓰지 않습니다.
5. 실패를 수정하면 같은 사례와 변경 영향을 받는 기존 정상 동작을 다시 검사합니다.
6. 이전 증거는 관련 코드·설정·입력이 동일하고 여전히 유효할 때만 재사용합니다.
7. 화면 확인은 사용자에게 내장 미리보기의 조작 순서와 기대 결과를 안내하고, 회신 전에는 미확인으로 둡니다.
8. 문서의 수치·설명, 필수 저장 경로와 저장 상태를 실제 결과와 대조합니다.

자동 브라우저 조작·화면 캡처 자동화는 실행하지 않는 구성입니다.
금지된 기존 검사를 생략하면 그 이유와 범위를 표시하며, 실패를 숨기려고 검사를 삭제하지 않습니다.

### 출력

`조건 / 파일·설정·입력 버전 / 명령 / 기대 결과 / 실제 결과 / 통과·실패·미확인`

기록 양식이 필요할 때만 [evidence-log.md](skills/kit-verify/references/evidence-log.md)를 참고합니다.
이 파일은 빈 양식이며 실행 이력이 아닙니다. 과제 지정 양식이 있으면 그것을 우선합니다.

### 호출 예시

```text
$kit-verify 현재 과제를 검증해 주세요.
```

### 기대 출력 예시

가상 규칙이 “유효한 측정값 10 초과이면 경고”일 때, 다음은 **보고 형식 예시이며 실제 실행 결과가 아닙니다.**

| 조건 | 기대 결과 | 실행 근거가 없을 때 표시 |
|---|---|---|
| 값 10 | 경고하지 않음 | 미확인 |
| 값 10.1 | 경고함 | 미확인 |
| 값 누락 | 정해진 누락 정책 적용 | 정책 미확정 또는 미확인 |
| 사용자가 보는 화면 | 검사 결과와 일치 | 사용자 확인 전 미확인 |

실제로 실행해 관찰한 뒤에만 해당 항목을 통과·실패로 바꿉니다.
빌드 성공은 모든 기능의 정상 동작을 의미하지 않고, 일부 테스트 통과도 전체 요구 충족의 증거는 아닙니다.

### 사용자가 확인할 것

검사 명령과 실제 출력이 연결되는지, 아직 실행하지 않은 부분을 통과로 처리하지 않았는지 봅니다.
디스크 내용과 에디터의 미저장 편집이 다르면 필요한 내용을 보존한 뒤 차이를 해결해야 합니다.
제출 확정 버튼은 사용자가 누릅니다.

<summary><strong>④ kit-debug — 오류 재현에서 최소 수정·회귀 검사까지</strong></summary>

원문: [skills/kit-debug/SKILL.md](skills/kit-debug/SKILL.md)

### 언제 사용하나요?

버그·테스트 실패·예상과 다른 출력의 원인이 불명확하거나, 수정할수록 다른 기능이 깨질 때 사용합니다.
원인과 수정 범위가 이미 확정된 단순 편집에는 생략합니다.

### 입력

재현 입력과 순서, 민감값을 제거한 오류 메시지, 기대 결과, 실제 결과, 최근 변경입니다.
원본 문제·로그를 외부 서비스로 보내는 방식이 아니라 허용된 작업 환경 안에서 확인합니다.

### 진행 방식

1. 같은 입력으로 재현하고 오류 위치·종료 코드·관련 파일을 확인합니다.
2. 최근 변경과 `입력 → 검증 → 처리 → 저장 → 출력`을 추적해 처음 기대와 달라지는 경계를 찾습니다.
3. 원인 가설 하나와 그 가설이 틀렸을 때 관찰할 결과를 적고 작은 검사를 합니다.
4. 가능한 경우 실제 결함을 검출하는 테스트를 먼저 실행합니다.
5. 관련 부분만 최소 수정합니다. 여러 설정 변경이나 무관한 리팩토링을 묶지 않습니다.
6. 같은 실패 입력과 기존 정상 흐름을 다시 실행합니다.
7. 반복 실패하면 같은 수정을 되풀이하지 않고 가설과 증거를 다시 봅니다.
8. 플랫폼·감독·인증 문제라면 사용자 코드로 우회하지 않고 제공된 문의 절차로 넘깁니다.

### 출력

`재현 여부 / 최초 차이 / 원인과 근거 / 변경 파일 / 동일 검사 재실행 / 남은 위험`

재현되지 않는 오류는 “해결”이 아니라 부족한 관찰을 남깁니다.
환경변수 전체·인증 파일·키·토큰을 조사하거나 출력하지 않습니다.

### 호출 예시

```text
$kit-debug 현재 오류를 해결해 주세요.
```

### 기대 출력 예시

자체 합성 사례로, 미확인 초안의 발행을 거부해야 하는데 발행이 성공하고 상태 검사가 빠졌음이 확인됐다면,
재현 요청·실제 동작·누락 위치·수정 파일·차단 재검사·정상 경로 재검사를 이어서 보고합니다.
상태 검사 누락은 예시일 뿐이며, 실제 코드를 읽기 전에 원인으로 단정하면 안 됩니다.

### 사용자가 확인할 것

원인 근거 없이 큰 파일 묶음을 바꾸지 않았는지, 테스트의 기대값을 낮춰 실패를 숨기지 않았는지 확인합니다.
`kit-verify`가 실패를 발견했다면 이 스킬로 원인을 좁히고, 수정 후 영향받은 완료 조건을 다시 검증합니다.

### 언제 사용하나요?

사전 연습 또는 제출물 확정 전에, 내가 선택한 방식과 실제 구현을 연결해 이해할 때 사용합니다.
**제출 확정 후, 질문 생성 대기 중, AI 사용이 금지된 실제 서술형 단계에서는 중단합니다.**

### 입력

현재 코드, 확정 요구, 사용자가 실제로 한 결정, 실제 검증 기록입니다.
이전 대화나 검증 기록이 없으면 있었다고 추측하지 않습니다.

### 진행 방식

1. 중요한 선택 1~3개부터 설명하되 필수 흐름이나 요청 범위를 누락하지 않습니다.
2. 각 선택을 `요구 → 선택 → 구현 위치 → 검증 → 한계`로 연결합니다.
3. 대표 입력 하나가 지나가는 파일·함수·상태와 최종 출력을 실제 코드에서 추적합니다.
4. 실제로 검토한 대안만 설명하고 사람의 결정·AI의 제안·관찰·추론을 구분합니다.
5. 기본 출력으로 현재 프로젝트 요약과 심화 서술형 연습 10문항·설명 답안·근거·꼬리 질문·보조 암기 단서를 만듭니다. 알고리즘의 원리·보장 범위·취약 입력과 AI·담당자 협업의 실제 결정을 다루되 코드·기록에 없는 내용은 미확인으로 둡니다. 사용자가 문답 모드를 요청할 때만 한 문제씩 묻습니다.
6. 공개 평가 방식에서 연습 관점을 도출하되 실제 기출·예정 문항·공식 모범답안으로 주장하지 않습니다.

### 출력

`프로젝트 전체 요약 / 중요한 결정·실제 코드 근거 / 대표 입력 처리 흐름 / 서술형 연습 10문항·답안·암기 단서 / 검증 범위·미확인·한계`

설명을 생성했다는 사실은 사용자가 이해했다거나 실제 동작을 검증했다는 증거가 아닙니다.
사용자의 판단이 아니었던 것을 “내가 결정했다”로 바꿔 쓰지 않습니다.

### 호출 예시

```text
$kit-explain 현재 구현을 설명해 주세요.
```

### 기대 출력 예시

구현에서 실제 확인되는 경우에만 다음 연결을 설명합니다.

> 요구: 확인된 답변으로만 피드백합니다.
> 선택: 처리 단계에서도 확인 상태를 검사했습니다.
> 위치: 실제 코드에서 확인한 파일·함수입니다.
> 검증: 실제 실행 기록이 있는 입력과 결과만 설명합니다.
> 한계: 상태 검사가 생성된 피드백의 모든 내용까지 옳음을 보장하지는 않습니다.

파일명이 없으면 임의의 함수명을 만들어 넣지 말고 추가 확인이 필요하다고 표시해야 합니다.

### 사용자가 확인할 것

설명이 내 코드와 맞는지, 선택의 이유와 남은 한계를 본인 말로 다시 설명할 수 있는지 확인합니다.
복습을 끝내고 제출을 확정한 뒤에는 이 스킬을 다시 호출하지 않습니다.

## 5. 한 과제에서 이어 쓰는 예시

아래는 **검사 CSV를 읽어 검토 대상을 보여주는 도구를 만든다는 자체 연습 가정**입니다.
실제 출제 내용이나 의무적인 기술 스택을 의미하지 않습니다.

1. **`kit-brief`**: 과제 문서의 필수 기능과 완료 조건을 정리합니다. 담당자에게 필요한 질문은 사용자에게 제안합니다.
2. **`kit-data`**: 한 행의 의미, 제품 키, 검사 차수, 기준 문서, 재검사·누락 처리 등을 확인합니다.
3. **기본 Codex**: 확정된 조건으로 `파일 읽기 → 입력 검사 → 결과·근거 표시` 흐름 하나를 구현합니다. 전용 구현 스킬은 없습니다.
4. **`kit-verify`**: 작은 입력의 기대값과 실제 결과를 비교합니다. 화면은 사용자가 내장 미리보기에서 확인합니다.
5. **`kit-debug`**: 재검사 때문에 집계가 잘못된 경우처럼 원인이 불명확한 실패만 분석하고 수정합니다. 이후 관련 검사를 다시 합니다.
6. **`kit-explain`**: 제출 확정 전에 집계 기준·입력 검사·실패 처리 등의 실제 결정과 근거를 복습합니다.

담당자가 “최종 검사 기준으로 바꿔 주세요”라고 실제로 답했다면:

```text
담당자 답변은 다음과 같습니다: [실제로 받은 답변]
기존 가정과 달라진 조건을 확인하세요.
집계·표시·검증·설명 중 영향받는 부분만 갱신하고 관련 검사를 다시 실행하세요.
```

문서 전체를 다시 만들거나 동일한 감사를 전부 반복하지 말고 변경 영향에 집중합니다.

## 6. 유의미한 사용인지 판단하는 기준

이 키트의 목적은 **좋은 작업 지시를 재사용하고 중요한 확인의 누락을 줄이도록 돕는 것**입니다.
동일한 절차를 사용자 요청에 써도 유사한 지시가 됩니다. 별도의 지능이나 채점 보너스를 추가하지 않습니다.

| 스킬 | 사용 후 관찰할 변화 | 효과가 없거나 과한 사용 |
|---|---|---|
| `kit-brief` | 요구마다 근거·완료 조건이 있고 가정이 드러남 | 실행 없이 계획 문서만 계속 늘림 |
| `kit-data` | 키·단위·분모·재검사 해석을 계산 전에 확인함 | 확인하지 않고 “데이터 정제 완료”만 보고함 |
| `kit-verify` | 명령·입력·기대값·실제값·상태가 연결됨 | 로그 없이 완료 선언 또는 무조건 전체 검사 반복 |
| `kit-debug` | 재현 근거와 최소 수정, 회귀 검사가 연결됨 | 원인 가설 없이 여러 설정을 동시에 변경함 |
| `kit-explain` | 실제 파일·함수·결정·검증의 연결을 설명함 | 존재하지 않는 구현과 사람의 결정을 만들어냄 |

위 항목은 **평가 기준 제안**이지 측정된 개선 효과가 아닙니다.
동일 과제·같은 모델에서 사용 전후의 정확도·시간·토큰·점수 비교를 수행하지 않았습니다.
설치기 테스트 통과도 모델이 모든 지침을 지킨다는 뜻이 아닙니다.

시간이 부족하면 새 스킬을 추가하기보다 이미 받은 결과에서 중요한 요구 하나를 실제로 확인하세요.
준비된 문서를 전부 읽히거나 매 작업마다 다섯 스킬을 순서대로 강제하지 않습니다.

## 7. 설치 문제와 중단 기준

**설치 완료 메시지가 나왔는데 스킬이 안 보입니다.**
파일 배치와 자동 인식은 다릅니다. 설치된 `KIT.md`와 해당 `SKILL.md`의 경로를 대화에서 명시해 읽히세요.
고정된 Codex 버전을 업데이트하거나 관리 설정을 수정하지 않습니다.

**`KIT.md`나 동명 스킬 내용이 다르다고 중단됩니다.**
기존 파일을 지키기 위한 동작입니다. 강제 덮어쓰기나 삭제로 해결하지 말고 현재 자료와 차이를 확인하세요.
같은 키트라도 버전이 달라지면 이 충돌이 발생할 수 있습니다. 새 버전이라는 이유로 기존 과제용 수정까지 교체하지 않습니다.
설치하지 않고 다운로드한 폴더의 지침을 명시적으로 읽는 방법도 있지만, 과제 규정·접근 권한이 우선입니다.

**다른 터미널에서 `kit_dir` 변수를 찾지 못합니다.**
첫 복제 명령과 설치 명령은 같은 셸에서 실행하세요. 다른 셸에서는 복제된 폴더의 실제 경로를 사용합니다.
새 대화를 만들거나 복제를 반복하기 전에 기존 폴더가 어디인지부터 확인하세요.

**Windows PowerShell에서는 어떻게 하나요?**
설치기는 Bash와 `cp`, `cmp`, `diff`, `find`, `mkdir` 등 명령을 사용하는 구성입니다.
PowerShell 전용 설치기는 없습니다. 제공된 웹 IDE의 Bash 계열 셸에서 사용하는 방식이며,
해당 셸이 없다면 환경을 임의로 바꾸지 말고 안내를 확인하거나 파일을 읽는 방식으로 진행하세요.

**다운로드·실행이 막혔거나 감독/플랫폼 오류가 납니다.**
도구·접속 경로·권한 설정을 바꿔 제한을 우회하지 않습니다. 제공된 문의 절차로 확인합니다.
설치에 매달리기보다 기본 제공 환경에서 필수 작업을 진행할 수 있는지 판단하세요.

## 8. 허용 범위·검증·파일 안내

### 준비물과 실제 시험 작업의 경계

현재 과제 안내와 최신 운영 규정이 우선입니다. 이 키트 자체가 반입 허가를 의미하지 않습니다.
공개 자료만 허용되는 환경에서는 저장소를 요구 기간까지 공개로 유지해야 합니다.
시험 문제·메일·개인 접속 링크·자격증명·비공개 코드·실제 제출물은 이 저장소에 넣지 마세요.

준비용 공개 자료를 받는 Clone과, 실제 작업을 외부로 보내는 Push는 구분합니다.
작업 중 문제·데이터·코드·로그의 외부 전송, 배포, 외부 모델 연결을 하지 않습니다.
키트는 Computer Use와 브라우저 자동 조작을 사용하지 않는 보수적인 구성을 취합니다.
플랫폼 관리·감독 설정 변경, 자동 제출, 새 토큰 생성도 수행하지 않습니다.
AI 사용 금지 단계와 제출 확정 후 질문 생성 대기 중에는 설명·첨삭·답안 생성도 중단합니다.

### 실제로 확인한 범위

[CHECKS.md](CHECKS.md)에 실행 결과를 기록합니다. 키트 저장소 루트에서 개발용 검사를 실행할 수 있습니다.
시험 중 반드시 실행해야 하는 과정은 아닙니다.

```bash
bash -n install.sh
python3 -m unittest discover -s tests -v
```

검사는 파일 배치·기존 파일 보존·동일 재설치·충돌 선검사·링크/잘못된 경로 차단·기본 메타데이터를 대상으로 합니다.
전체 설치 파일의 바이트 일치, 기존 에이전트 설정·다른 스킬 보존, 공백·한글 경로도 검사합니다.
Windows의 개발용 테스트는 설치된 Git Bash를 사용하며, 심볼릭 링크 생성 권한이 없으면 해당 두 검사를 skip으로 보고합니다. 이는 설치기를 PowerShell용으로 바꾸거나 권한을 자동 변경하는 동작이 아닙니다.
설치기에 금지된 명령 문자열이 없는지 확인하는 검사도 있지만, 완전한 보안 감사나 동적 네트워크 감시를 의미하지 않습니다.
실제 플랫폼 자동 인식, 모든 운영체제, 모델의 지침 준수, 점수·속도·토큰 개선은 검증하지 않았습니다.
