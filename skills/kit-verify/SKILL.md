# 완료 판정의 근거 만들기

## 입력
확정된 완료 조건, 현재 코드·설정·입력 버전, 최근 변경, 기존 실행 로그.

## 처리
1. 조건별로 실제 기능/파일이 있는지 봅니다. 빈 양식과 placeholder를 완성으로 보지 않습니다.
2. 해당 실행 환경에 맞는 최소한의 빌드·순수 로직·로컬 API 검사를 실제로 실행합니다.
3. 정상·경계·누락·중복 요청·실패 중 요구사항을 깨뜨릴 가능성이 높은 사례를 고릅니다.
4. 예상 결과는 문서와 확정한 업무 규칙에서 정합니다. 테스트 삭제·기대값 완화로 실패를 숨기지 않습니다.
5. 실패한 조건을 수정한 뒤 동일 사례와 변경 영향을 받는 정상 동작을 다시 검사합니다.
6. 이미 실행한 증거는 코드·설정·데이터가 해당 범위에서 동일하고 여전히 유효할 때만 재사용합니다.
7. 화면은 사용자에게 내장 미리보기의 짧은 조작과 기대 결과를 안내합니다. 회신 전에는 미확인으로 둡니다.
8. 자동 브라우저 조작/화면 캡처 자동화는 실행하지 않습니다. 금지된 기존 검사는 건너뛴 이유와 범위를 표시합니다.
9. 문서 수치와 현재 구현·결과가 일치하는지, 지정한 필수 경로와 저장 상태가 맞는지 확인합니다.
10. 제출 동작은 사용자가 합니다. 제출 확정 전에만 작업합니다.

## 테스트 결과를 읽는 기준
- 실행 명령과 종료코드뿐 아니라 수집·실행·통과·실패·오류·건너뜀 수를 확인합니다. 러너가 제공하지 않은 수치는 추측하지 않습니다.
- 테스트 0개, 전부 건너뜀, TODO만 있는 실행은 기능 검증 성공이 아닙니다. 프로세스가 0으로 종료돼도 해당 조건은 미확인으로 둡니다.
- 일부 건너뜀이 있으면 실제 통과 범위와 건너뛴 범위를 나눕니다. 검사를 실행하지 않은 사유와 다른 근거의 필요 여부를 남깁니다.
- 종료코드가 0이어도 로그에 실패·오류가 있으면 통과로 선언하지 않습니다. 실패를 덮은 래퍼, 여러 명령의 마지막 종료코드, stdout/stderr 차이를 확인합니다.
- 종료코드가 0이 아닌데 로그 요약만 성공이면 통과로 판정하지 않습니다. 실패·오류가 확인되면 실패, 원인을 확인하지 못한 충돌은 미확인으로 남기고 명령과 전체 로그를 확인합니다.
- 출력이 잘렸거나 요약이 충돌하거나 형식을 해석할 수 없으면 판정 보류·미확인으로 기록합니다. 실제 실행 출력과 예시 문자열을 구별합니다.
- 빌드나 데이터 계산처럼 테스트 러너가 아닌 검사는 테스트 개수를 억지로 요구하지 않습니다. 그 작업의 종료코드·산출물·기대 결과로 확인합니다.

## 기존 증거를 재사용할 때
검사 시각과 시간대, 작업 위치, 관련 소스·테스트·설정·의존성·입력의 식별 정보를 기존 기록에 남깁니다.
커밋만으로 미커밋 변경까지 증명하지 않습니다. 필요한 경우 관련 파일만 해시로 비교하되, 전체 작업공간·인증 파일을 수집하지 않습니다.
검사 후 관련 내용이 바뀌었거나 변경 여부를 확인할 수 없으면 현재 통과로 재사용하지 말고 영향받는 검사만 다시 실행합니다.
선택한 파일이 같아도 외부 상태·미추적 의존성이 같다는 보장은 없습니다. 파일 동일성과 테스트 성공·요구 충족을 구분합니다.
이 키트에 자동 로그 판정기나 파일 변경 감시기는 없습니다. 위 확인은 제공된 에이전트와 허용된 도구로 수행합니다.

## 출력
조건 / 버전·명령·입력 / 기대 결과 / 실제 결과 / 통과·실패·미확인.
성공 주장에는 실행 근거를 연결하고, 부분 검사를 전체 완료로 확대하지 않습니다.
추가 양식이 필요할 때만 references/evidence-log.md를 참고합니다.


## 공통 경계
현재 과제 지침을 우선하고 KIT.md를 보조 원칙으로 사용합니다. 원문 데이터 보존, 외부 전송 금지, 설정 변경 금지, 미실행의 미확인 표시를 지킵니다. AI 사용 금지 단계에는 사용하지 않습니다.
